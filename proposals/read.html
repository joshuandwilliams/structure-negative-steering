proposals/00-README.md

Simplification proposals, one file per script

Read these in number order. Each is independent, so you can accept one and reject the next. Nothing here is applied to bin/.

What I measured, and what I did not

Two goals, and they pull in different directions often enough to be worth separating.

Shorter and plainer. Measured as lines, and as how many of those lines are mechanical: out["x"] = r.get("x", "") repeated forty times is forty lines carrying one idea. The repo-wide count of that pattern is 191 assignments.

Faster. Measured by benchmark, not by reasoning. This matters less than it sounds, and the reason is worth stating once: every stage's wall-clock is dominated by singularity exec … boltz predict, which is minutes to hours. From analysis/03-compute-cost/runtime_comparison.csv, one steered benchmark target is 19.5 to 263 minutes depending on dose. Python that reads a few thousand CSV rows is milliseconds against that. So shaving Python almost never shows up in a run, and I have not pretended otherwise in these files.

The exception is algorithmic: a loop that re-reads a file, or re-walks a directory tree, once per item. Two of those exist and both are in here. They are the only changes where the speed claim is the point rather than a footnote.

Where a rewrite would be slower, I say so and do not propose it.

How each proposal is verified

Every proposal that changes behaviour-bearing code carries two checks before it is offered:

  1. Fixture equality. The old and new implementations run over every relevant input the repo holds, and their outputs are compared field by field. For row builders that is 151 aggregated_results.csv rows; for structure readers it is the 18 complexes in data/reference_complexes/.
  2. Randomised equality. Thousands of generated inputs covering each branch, including the outcome classes and absent keys, since the fixtures do not reach every path.

Then the suite runs, and coverage has to stay at 100%. A proposal that fails any of those is not in this folder.

proposals/01-sum_stage_times.md

01 — bin/sum_stage_times.py, 47 lines

Proposal: change nothing.

This is the whole file minus its docstring: 24 statements, two functions.

def total_seconds(stage_times: Path) -> int:
    if not stage_times.is_file():
        return 0
    total = 0
    for line in stage_times.read_text().splitlines():
        parts = line.split()
        if len(parts) == 2 and parts[1].lstrip("-").isdigit():
            total += int(parts[1])
    return total


def main(argv: list[str]) -> int:
    ap = argparse.ArgumentParser(description=__doc__)
    ap.add_argument("--stage-times", type=Path, required=True)
    ap.add_argument("--output", type=Path, required=True)
    args = ap.parse_args(argv)
    args.output.write_text(f"{total_seconds(args.stage_times)}\n")
    return 0

Is every line necessary

Yes. Taking them in turn:

  • is_file() guard: a missing .stage_times has to give 0 rather than raise, because POSTPROCESS runs it unconditionally and a stub run has no stage times. Removing it turns an expected case into a stage failure.
  • len(parts) == 2: the file is appended to concurrently by tasks on different nodes over a shared filesystem, so a torn line is possible. The module docstring records that one predict_one line was lost that way on the first cluster run. A line that is not exactly two fields is skipped rather than guessed at.
  • lstrip("-").isdigit(): skips a non-numeric second field without raising. Same reason.
  • total += int(parts[1]) inside the loop rather than sum(...) over a comprehension: a comprehension would need the same two guards in a filter and would read worse, not better.

Could it be shorter

Marginally, and it would be worse. The comprehension version:

return sum(int(p[1]) for p in (l.split() for l in text.splitlines())
           if len(p) == 2 and p[1].lstrip("-").isdigit())

That is one line instead of six and I would not take it. The guard conditions are the interesting part of this function, and burying them in a nested generator makes the one thing worth reading hard to find.

Speed

Irrelevant and not worth measuring. The file it reads has one line per stage, so ten lines on a real run. This runs once per target.

What changes

1. The directory routing, 19 lines → 8

The current code picks the directory to search with a three-branch if/elif/else, where two branches differ only in how they build the suffix:

if prediction_pdb.name == "initial_prediction.pdb":
    experiment_root = prediction_pdb.parent
    initial_dir = experiment_root / "initial"
    if initial_dir.is_dir():
        design_dir = initial_dir
    else:
        design_dir = experiment_root

      and prediction_pdb.name.endswith(".pdb")):

The two initial cases are one case. initial_prediction.pdb has an empty suffix and initial_prediction_s2.pdb has _s2, so slicing after initial_prediction rather than after initial_prediction_ gives both:

def _sidecar_search_dir(prediction_pdb: Path) -> Path:
    """Where to look for the nested model PDB.

    A design's sidecars are under the design directory. The cold-start
    baselines are not: boltz2_negative_steering.py writes
    `<root>/initial_prediction.pdb` with sidecars in `<root>/initial/`, and
    `<root>/initial_prediction_s<N>.pdb` with sidecars in
    `<root>/initial_s<N>/`. Routing each to its own seed directory is what
    stops the glob picking up a sibling seed's PDBs.
    """
    name = prediction_pdb.name
    if not name.startswith("initial_prediction") or not name.endswith(".pdb"):
        return prediction_pdb.parent
    root = prediction_pdb.parent
    suffix = name[len("initial_prediction"):-len(".pdb")]   # "" or "_s1"
    seed_dir = root / f"initial{suffix}"
    return seed_dir if seed_dir.is_dir() else root

Pulling it out as its own function is what makes the docstring possible. In place it was a comment block in the middle of a longer function.

2. resolve() hoisted out of the loop — this is the speed part

for p in design_dir.rglob("*.pdb"):
    if p.resolve() == prediction_pdb.resolve():      # ← right-hand side
        continue                                     #   never changes

Path.resolve() makes syscalls. prediction_pdb is the function's argument, so the right-hand side is the same on every iteration. Hoisting it:

target = prediction_pdb.resolve()
candidates = [p for p in search_dir.rglob("*.pdb")
              if p.resolve() != target and "msa" not in p.parts]

Measured over 20 calls each, on a tree with N nested PDBs:

Nested PDBs Current Proposed Speedup
5 2.13 ms 1.63 ms 1.31×
25 6.07 ms 4.86 ms 1.25×
125 26.92 ms 17.08 ms 1.58×

Small in absolute terms. It is in here because it costs nothing to take: the list comprehension is also the shorter form.

3. The duplicated sort key, two copies → one named function

with_conf.sort(key=lambda p: ("model_0" not in p.name and "rank_0" not in p.name, str(p)))
...
candidates.sort(key=lambda p: ("model_0" not in p.name and "rank_0" not in p.name, str(p)))
return candidates[0]

Two identical five-line lambdas, each followed by taking element zero. That is min with a named key:

def _sidecar_rank(pdb: Path) -> tuple:
    """Sort key preferring Boltz's first-ranked model."""
    return ("model_0" not in pdb.name and "rank_0" not in pdb.name, str(pdb))

with_conf = [p for p in candidates if _has_confidence(p)]
return min(with_conf or candidates, key=_sidecar_rank)

min rather than sort also stops doing an O(n log n) sort to read one element. with_conf or candidates is the whole of the preference rule: use the ones with a confidence JSON if there are any, else all of them.

_has_confidence moves from a nested function to a module-level one, because it closes over nothing and is six lines of or rather than two ifs and a return False.

Verification

  • Every .pdb in tests/characterization/fixtures, 4 of them: identical results.
  • Synthetic trees covering all three routing branches × sidecar directory present or absent, 6 cases: identical results.

Is every line necessary

In the proposed version, yes. The one thing I considered cutting and did not is the "msa" not in p.parts filter. It skips cached reference structures that Boltz writes under msa/, and without it a cached reference can win the _sidecar_rank comparison and send compute_metrics at the wrong structure. The comment on it says "skip cached reference structures", which is the reason, so it stays.

proposals/04-compute_metrics-sidecars.md

04 — bin/compute_metrics.py, the sidecar lookup

Proposal: accept. This is the one change where speed is the point. 96× faster at the benchmark's own model count, and 24 lines shorter.

The problem

parse_boltz2 walks pred_dir once to find the model PDBs, then for each PDB looks up three sidecars: confidence_<name>.json, plddt_<name>.npz and pae_<name>.npz. Each lookup is three globs chained together, and the third one is recursive:

conf_files = _dedup_paths(
    glob.glob(os.path.join(pdb_dir, f"confidence_{name}.json")) +
    glob.glob(os.path.join(pdb_dir, "..", "confidence", f"confidence_{name}.json")) +
    glob.glob(os.path.join(pred_dir, "**", f"confidence_{name}.json"), recursive=True)
)

pred_dir does not change across the loop. So that third glob walks the whole output tree, and it happens three times per PDB. At 25 models — 5 seeds × 5 diffusion samples, the benchmark's own setting from experiments/benchmarking/*/config.yml — that is 75 recursive walks of the same directory.

The change

Walk once before the loop, index by filename, look up by key.

def _sidecar_index(pred_dir):
    """Map every filename under pred_dir to its paths, nearest first."""
    index = {}
    for dirpath, _dirnames, filenames in os.walk(pred_dir):
        for nm in filenames:
            index.setdefault(nm, []).append(os.path.join(dirpath, nm))
    for paths in index.values():
        paths.sort(key=lambda p: (p.count(os.sep), p))
    return index


def _sidecar(index, pdb_dir, name, kind, ext):
    """The best path for one sidecar, or None."""
    filename = f"{kind}_{name}.{ext}"
    candidates = index.get(filename, ())
    if not candidates:
        return None
    here = os.path.join(pdb_dir, filename)
    sibling = os.path.normpath(os.path.join(pdb_dir, "..", kind, filename))
    for preferred in (here, sibling):
        for c in candidates:
            if os.path.normpath(c) == preferred:
                return c
    return candidates[0]

Then each of the three lookups becomes one line:

conf_file  = _sidecar(index, pdb_dir, name, "confidence", "json")
plddt_file = _sidecar(index, pdb_dir, name, "plddt", "npz")
pae_file   = _sidecar(index, pdb_dir, name, "pae", "npz")

The three kind values are also the sibling directory names, which is Boltz's own convention: confidence_x.json lives either beside the PDB or in a sibling confidence/. That is what lets one helper serve all three and removes the only use of _dedup_paths.

Preference order is preserved exactly, which is the thing that had to be got right because the caller takes element zero. The old order was: beside the PDB, then the sibling category directory, then anywhere in the tree. The new code checks those two explicit locations first and falls back to the shallowest remaining path.

Speed, measured

Built a Boltz-shaped output tree and timed the three lookups across all PDBs:

Models Files in tree Current Proposed Speedup
5 60 12.8 ms 0.8 ms 16×
25 300 78.3 ms 0.8 ms 96×
125 1,300 559.4 ms 2.3 ms 244×

The honest context: negsteer_aggregate.py runs compute_metrics.py as a subprocess per passing row, so a benchmark target makes tens to low hundreds of these calls. At 78 ms each that is a few seconds per target against a run of 19.5 to 263 minutes. So this does not shorten a run noticeably. It is worth taking because the code is shorter as well, not because it saves time.

Where it would matter is a dose-sweep arm at n=50 with many passing rows, and on a shared filesystem where each stat is a network round trip rather than a local one. I have not measured that, and I will not claim it.

Verification

  • Both Boltz output trees in tests/characterization/fixtures: 3 lookups per PDB, identical paths.
  • 300 synthetic trees with the sidecar randomly present beside the PDB, in a sibling confidence/, deeper in the tree, or in several of those at once: 906 lookups total, zero differences.

Line count

24 lines out. The three 5-line glob chains become three 1-line calls, _dedup_paths and its docstring go, and the two new helpers cost 30 lines including their docstrings.

Is every line necessary

os.path.normpath on both sides of the comparison is. Without it a/pdb/../confidence/x.json and a/confidence/x.json are different strings for the same file, and the sibling-directory preference would never match. That is exactly what the old glob did implicitly by resolving the pattern.

05 — bin/negsteer_coldstart.py, the reversion-plan lookup

Proposal: accept. The second of the two changes where speed is the point. 40× at the benchmark's dose, 77× at n=50, and four lines shorter.

The problem

Inside cmd_kickoff_finalize's loop over candidates, for every candidate whose verdict is pose_holds:

rp_path = cycle0_dir / "reversion_plan.json"
if rp_path.exists():
    rp = json.loads(rp_path.read_text())
    for entry in rp.get("entries", []):
        if entry.get("label") == label:
            reverted_fasta = Path(entry["reverted_receptor_fasta"])
            break

cycle0_dir is fixed for the whole stage, so this re-reads and re-parses the same JSON file once per candidate, then linearly scans its entries. Both costs grow with the number of designs, so the whole thing is O(n²) in designs.

The change

Read it once before the loop and index by label:

# reversion_plan.json is read once rather than per candidate: the file is
# the same for the whole stage, and scanning its entries per candidate made
# the lookup quadratic in the number of designs.
reverted_fasta_by_label = {}
rp_path = cycle0_dir / "reversion_plan.json"
if rp_path.exists():
    for entry in json.loads(rp_path.read_text()).get("entries", []):
        reverted_fasta_by_label.setdefault(
            entry.get("label"), entry.get("reverted_receptor_fasta"))

and in the loop:

fasta = reverted_fasta_by_label.get(label)
reverted_fasta = Path(fasta) if fasta else None

setdefault rather than [...] = is deliberate: the old loop breaks on the first matching label, so a duplicated label took the first entry. setdefault keeps that. Plain assignment would silently take the last, which is a different answer on a malformed plan.

Speed, measured

Entries are 3 per design, one per seed, which is what write_reversion_plan emits. Timed over the full candidate list:

Designs Plan entries Current Proposed Speedup
3 9 1.6 ms 0.20 ms 8×
20 60 14.1 ms 0.35 ms 40×
50 150 46.2 ms 0.60 ms 77×

20 designs is negsteer_n_designs in the committed benchmark configs; 50 is the n50 dose-sweep arm. The results were asserted equal inside the benchmark, so the measurement and the correctness check are the same run.

Same honest context as 04: 46 ms is nothing against a run of hours. It is worth taking because the code is shorter and the quadratic term goes away, so it will not surprise anyone at a larger dose.

Is every line necessary

The rp_path.exists() guard is. A run where no design was contaminated writes no reversion_plan.json, and cmd_kickoff_finalize runs regardless, so the missing file is an expected case rather than an error. Without the guard that run raises instead of finalising.

The if fasta else None is, for the same reason: a label with no plan entry is the missing_verdict path a few lines above, which is handled rather than fatal.

06 — bin/extract_passing.py, 629 lines

Proposal: accept. 6.1× faster per row, 243 → 161 lines on the part that changes, and it closes a defect that grows sys.path without bound.

This file is where I started, and the benchmark found something I was not looking for. Read the second change first: it is the important one.

Code for all three parts is in proposals/code/06-*.py.

Change 2 first: _compute_confidence_flag re-imports on every call

if pass_frac_min is None or iptm_min is None or ...:
    try:
        import sys
        sys.path.insert(0, str(Path(__file__).resolve().parent))
        from pipeline_thresholds import PipelineInternalThresholds
        _t = PipelineInternalThresholds.default()

This runs once per row. Three consequences, in order of seriousness.

It grows sys.path without bound. There is no if not in sys.path guard, so every call appends another copy of bin/. Measured: 500 calls add 500 duplicate entries. Every import after that searches a longer path.

The repo already asserts this must not happen. From tests/characterization/test_modules_repair_sys_path.py:66:

test_a_module_already_on_the_path_does_not_duplicate_it — "The guard is there so a repeated import cannot grow sys.path without bound."

That test covers the module-level inserts. This function has the same bug and no guard.

It dominates the runtime. Profiling extract_row over the fixture rows: _compute_confidence_flag is 1.634 s of 2.005 s cumulative, 82%. Inside it, Path.resolve() → realpath → _joinrealpath is about 1.0 s, half of extract_row's total time, spent re-resolving __file__.

The fix resolves the thresholds once at import and turns the four near-identical try/float/compare blocks into one table:

_CONFIDENCE_CHECKS = (
    ("pae_pass_frac_median", "<", _DEFAULT_PASS_FRAC_MIN, "low_pass_frac", 1),
    ("iptm_median", "<", _DEFAULT_IPTM_MIN, "low_iptm", 1),
    ("complex_plddt_median", "<", _DEFAULT_COMPLEX_PLDDT_MIN, "low_plddt", 1),
    ("ipae_median", ">", _DEFAULT_IPAE_MAX, "high_ipae", 0),
)

The last column is the value used when the metric is absent, chosen so a missing metric does not trigger. That was implicit in the old code's out.get("iptm_median", 1) versus out.get("ipae_median", 0), and it is easy to get backwards, so it is now written down.

82× faster, and 24,000 randomised cases — every combination of the four metrics at threshold boundaries, absent, empty, and non-numeric, with and without explicit overrides — give identical flags.

Change 1: the column spec

extract_row is 152 lines for 62 statements, and 39 of those statements are out["x"] = r.get("x", ""). The 46 column names are also written out a second time in OUTPUT_FIELDS, so 93 name-spellings for 47 columns.

One ordered list of (column, rule) replaces both, and OUTPUT_FIELDS is derived from it:

OUTPUT_FIELDS = [c + "_median" if rule is CONF else c for c, rule in COLUMNS]

That matches the committed 47-entry list exactly, in order. Each column name is written once, and the two lists can no longer drift — which matters in one direction: csv.DictWriter raises on a key that is not a fieldname, but writes a blank for a fieldname the row never set, so a column extract_row forgot was silent.

extract_row's body becomes one loop per rule, six loops:

out = {}
for c in _AS_IS_COLS:
    out[c] = r.get(c, "")
for c in _STEERED_COLS:
    out[c] = r.get("steered_" + c, "")
...

I tried three forms and measured all of them

This is where the speed constraint changed the answer:

Form µs/row vs current
current, 39 straight assignments 87.1 1.00×
branch per column inside one loop 104.0 1.19× slower
out.update({...}) per rule 113.0 1.30× slower
plain for per rule, assigning into out 102.2 1.00×

The first two are the obvious ways to write it and both are meaningfully slower: a 47-iteration if/elif chain costs more than straight-line assignment, and .update() builds an intermediate dict and merges it, which is two passes. Only the plain per-rule loop is free, because it does exactly what the current code does with the column name coming from a tuple instead of a literal.

So the proposed form is the third one. I would have shipped the first without the benchmark.

Change 3: the mutation columns

The seven SEEDS columns are filled in an if per_seed_rows: branch and blanked in an else: that spells all seven out again. dict.fromkeys does the blanking, and the whole thing moves to its own function so the docstring can say why the steered set takes the first seed while the reverted set is summarised across seeds.

Current Proposed

extract_row lines 152 40
spec + extract_row lines 243 161
column names written 93 47

Verification

  • 151 aggregated_results.csv rows from the fixtures, with and without seed rows: identical.
  • 4,000 randomised rows across all six outcome classes with randomly absent keys on both the steered_ and reverted_ sides: identical.
  • 24,000 randomised confidence-flag cases: identical.

The try/except (ValueError, TypeError) around each float() is. proposals/09-cross_summary.md

09 — bin/cross_summary.py, 940 lines

Proposal: accept one small factorisation. Separately, a defect I found while verifying it, which is your call rather than mine. Read the defect section first.

The defect: tied ranks are not reproducible

_assign_cross_ranks breaks ties with id(rec):

def _composite_rank_key(item):
    comp, rec = item
    tier_order = _TIER_ORDER[rec["cross_tier"]]
    # Negated so higher composites come first within a tier.  id()
    # breaks ties as stably as Python's own sort would.
    return (tier_order, -comp, id(rec))

id() is the object's memory address. For two records with the same tier and the same composite, the rank order therefore depends on where Python happened to allocate the dicts.

Demonstrated: four records with identical tier and identical metrics, ranked three times in one process on freshly built objects.

ranks: [3, 2, 4, 1]
ranks: [3, 1, 4, 2]
ranks: [2, 3, 4, 1]

Three different answers for the same input. cross_rank_by_composite and cross_rank_by_ra_eff are columns in the committed cross_sequence_summary.csv, so a rerun of a cohort containing tied rows emits different ranks and the file does not reproduce.

The comment says id() "breaks ties as stably as Python's own sort would". That is not right. Python's sort is stable, meaning it preserves input order for equal keys. Using id() as a third key replaces that stability with an arbitrary order, so the comment describes the opposite of what the code does.

The fix is to delete the third key. list.sort is stable, so dropping id(rec) makes tied records keep the order they arrived in, which is the order the passing-summary inputs were read in, which is deterministic. That is one line removed and it makes the output reproducible.

I have not folded that into the proposal below, because it changes the committed output for any cohort with ties, and that is your call rather than mine. For the benchmark the question is narrow: each target is one sequence, so there is nothing to tie. For a campaign cohort with 128 sequences it is live.

The factorisation

The two rankings are the same five lines twice:

def _composite_rank_key(item):
    comp, rec = item
    tier_order = _TIER_ORDER[rec["cross_tier"]]
    return (tier_order, -comp, id(rec))

    rec["cross_rank_by_composite"] = rank_idx

    ra, rec = item
    tier_order = _TIER_ORDER[rec["cross_tier"]]
    return (tier_order, ra, id(rec))
scored_ra.sort(key=_ra_rank_key)

    rec["cross_rank_by_ra_eff"] = rank_idx

One helper, called twice:

def _stamp_ranks(scored, column: str) -> None:
    """Sort (value, rec) pairs tier-first and stamp 1-based ranks.

    `value` is already signed so that ascending order is "better first", so
    the caller negates a composite and leaves an ra_eff alone.
    """
    scored.sort(key=lambda pair: (_TIER_ORDER[pair[1]["cross_tier"]],
                                  pair[0], id(pair[1])))
    for rank_idx, (_value, rec) in enumerate(scored, start=1):
        rec[column] = rank_idx

with scored_composite.append((-comp, rec)) and scored_ra.append((ra, rec)) carrying the sign. 16 lines → 10, and the "better first" convention is stated once instead of implied twice.

What I did not merge. My first attempt replaced the whole function with a loop over the two metrics. It was wrong: the two rankings share a filter (row_type == "steered" and cross_tier in ("A","B","C")) but the composite branch also computes a derived value from two columns and stamps cross_composite_score as a side effect. A generic loop lost all three. The filter and the side effect stay written out.

Verification

3,000 randomised cohorts of 1 to 8 records across all four tiers, all three row types, with empty, nan and numeric metrics: identical, with one condition — metric values must be unique.

With ties allowed, 152 of 3,000 differed. That is not the factorisation: it is the id() tie-break above, comparing two deep copies at different addresses. Finding that is the only reason this file has a defect section.

Speed

Not measured, and I would not expect a difference. Both forms do one list.sort per ranking. A cohort is 1 record for the benchmark and 128 for a campaign.

Is every line necessary

The rec.get("row_type", "steered") != "steered" filter is. Control and cold-start rows are in the same record list and must not be ranked against steered designs — the docstring on _tier_for_row explains that controls "sit outside the cohort ranking by design". Removing the filter would rank a polyA control alongside a real design.
